## 连续内存分配 {#连续内存分配}

程序装入内存的时候占据一段物理地址 **连续** 的区域，CPU 只需要内存起始位置、内存长度两个信息即可确定程序内存。与之相对应的，离散内存分配允许一个程序内存拆分为若干块，分散在内存之中。

连续内存分配有两种模式：固定分区分配，动态分区分配。

其中，动态分区分配有如下分配算法：

-   顺序分配算法
    -   First Fit
    -   Next Fit
    -   Best Fit：查找最小可用分区进行分配
    -   Worst Fit：查找最大可用分区进行分配
-   索引分配算法：将分区按照大小进行分配，每一类分区通过链表连接，并通过索引表管理这些分区链表，从而在分区分配时可以根据所需空间大小准确定位到目标分区。
    -   Quick Fit：在索引表中找到能容纳作业长度的最小分区类别链表，找到链表中的第一个空闲分区，进行分配。
    -   Buddy System：
        1.  规定分区大小均为 \\(2^k\\)，需要分配的内存大小为 \\(2^{i-1}<n<=2^i\\)，令 j=i。
        2.  首先在大小 2^j 分区链中查找空闲分区。
        3.  如果没有空闲分区，则 j+=1 继续步骤 2；如果有空闲分区，则直接分配。
        4.  将该 \\(2^j\\) 分区不断二分，直到得到 \\(2^i\\) 大小的内存块，分配该内存块。这个过程中会产生 2 个 \\(2^i\\) 内存块，1 个 \\(2^{i+1}\\) 内存块……1 个 \\(2^{j-1}\\) 内存块。将它们全部加入不同的分区链表中。因而易见 Buddy System 中，每个 \\(2^k\\) 分区都有一个唯一的伙伴分区：与其大小相同，地址相邻，是在二分过程中得到的。
        5.  回收分区时，如果存在伙伴分区且伙伴分区也空闲，则合并为一个分区，并不断进行合并操作，直至无法合并。
    -   哈希算法：以分区大小为关键字，建立哈希函数，建立哈希表


## 离散内存分配 {#离散内存分配}

无论通过怎样的算法试图缓解，连续内存分配一定会出现这样的问题：系统的空闲内存可以满足需要，但是因为分散在各处，不能组成一段连续内存空间，因而无法分配。为了解决这个问题，我们可以允许一个程序内存拆分为若干块，分散在内存之中。


### 要实现离散内存分配，需要解决的问题 {#要实现离散内存分配-需要解决的问题}

程序所看到的内存永远是连续的，称之为逻辑地址。物理上程序的内存被拆分到内存各处，称之为物理。

因而需要一种机制将逻辑地址映射到物理地址。更具体地说，有如下问题：地址转化、访存速度、权限保护……

以上问题都只能在硬件层得到解决，只能通过 MMU、硬件相联存储器等方案得到解决。因而，只有在硬件得到发展的情况下，才能实现离散内存分配。


### 分页 {#分页}

想要解决的问题是：如何解决连续内存分配导致的内存碎片？

将物理内存划分为若干大小相同的单元，称为页框（page frame）；同时将逻辑地址空间划分为与页框大小相同的单元，成为页面（page）。系统以页框为单位给进程分配内存。

逻辑地址：\\(page number \cdot page offset\\)


#### 页表 {#页表}

os 为每个进程维护一个页表，页表实现页号到页框号的映射。

为了提高地址变换速度，系统通常设置一个页表寄存器（PTBR，在 x86 架构上为 CR3），存放页表地址和页表长度。

如果确定页表项（PTE, Page Table Entry）的大小？

1.  确定页大小（不依赖于页表设计，根据碎片、换入换出等情况决定）。通常为 4KB
2.  根据物理内存大小确定页框数。对于 32 位物理地址而言，内存 4GB，页框数为 4GB/4KB=2M=2^20。即页框位数为 20，因而物理地址的结构为：[高 20 位：页框号][低 12 位：页内偏移]
3.  从而页表项最小长度为 20 位。
4.  考虑到对齐、标志位等工程设计，一般页表项取 4B。


#### 快表（TLB） {#快表-tlb}

若页表全部存放在内存之中，每次访问内存至少需要两次访存，显著降低系统性能。因而可以增设一种高速缓冲存储器，快表（TLB，Translation Lookaside Buffter），用来存放最近访问过的页表项。相应的，主存之中的完整页表称为慢表。

因而，TLB 可以理解为页表的硬件 Cache，缓存“页号→页框号”的映射；与 Cache 的区别在于，页表由 OS 维护，页表变更后需要 OS 显式修正 TLB。

> 页表变更：
>
> -   缺页处理（os 把页从磁盘调入主存）
> -   页面换出
> -   进程创建与退出
> -   mmap, munmap, 堆栈增长
> -   写时复制
> -   ……

TLB 的硬件实现：

-   小规模 TLB，使用 CAM 实现，全相联策略
-   大规模 TLB，使用 SRAM+比较器实现，组相联策略

快表的有效性基于 **局部性原理**

### 分段 {#分段}

想要解决的问题是：内存的组织能不能匹配程序的结构？

分页管理由硬件自动完成，对用户完全透明；而 **分段管理对用户不透明** （因为分段要匹配程序本身的结构），段号。

| 分页        | 分段        |
|-----------|-----------|
| 系统管理内存的物理单位 | 用户程序的逻辑单位 |
| 对用户透明  | 对用户可见  |
| 页大小固定，系统决定 | 段大小不固定，程序决定 |


### 段页式存储管理 {#段页式存储管理}

进程的地址空间首先被分为多个逻辑段，对每个逻辑段进行页式管理。进程的逻辑地址有三个部分组成：段号、页号、页内偏移。


## 虚拟内存 {#虚拟内存}

以上探讨的所有内存管理策略，都是将多个进程 **一次性** 装入内存，并且只有在进程结束后，才能将进程的所有内存卸载（哪怕这个进程遇到了 I/O 阻塞等情况）。

然而根据局部性原理，程序在执行过程中，只需要将少数页面（段）装入内存，并在需要时进行请求调页（请求调段）和页面置换（段置换）。从而程序的逻辑空间大小可以远大于物理空间。我们可以将这个逻辑上存在的，但是物理上不存在的内存空间，成为虚拟内存。虚拟空间是对 os 的部分装入、请求调入、置换功能的抽象，虚拟内存是对用户透明的，在一般情况下，用户无需关注物理内存实际大小。

虚拟内存要得以实现，必须依赖局部性原理。进一步说，一个进程的内存空间，必须可以被划分为若干子集，因而虚拟内存必须在离散内存分配的基础上实现。

而在引入虚拟内存后， **内存管理可以划分为两个子问题：地址翻译与请求分页，物理页框分配** 。


### 局部性原理（Locality Principle） {#局部性原理-locality-principle}

> **All computational processes tend to refer repeatedly to subsets of their resources over extended time intervals.**

—— Peter J. Denning [doi](https://doi.org/10.1002/9780470050118.ecse960)

事实上，历史上的分页分段管理和虚拟内存技术是一起出现的。很少有只进行内存划分、地址翻译，而不实现虚拟内存的机器。

1962 年，Atlas 首次实现了请求分页。然而，设计者遇到了两个问题，地址翻译与页面置换策略。

在 1960 年代，各种虚拟内存的尝试都遇到了抖动灾难。

1966 年，IBM 在 Watson 实验室资助 Belady 等人系统评估置换策略，发现 LRU 置换策略是稳定最佳的置换策略，Belady 将这个现象归因于 reference clustering。

1967 年，Denning 定义了进程内在的内存需求：“This process needs p pages at time t”。并且在 Belady 的启发下，给出了形式化定义，工作集=过去固定长度窗口内用过的页的集合。

到 1980 年，局部性原理成熟，并可以被叙述为以下三点：

1.  Computational processes pass through a sequence of phases.
2.  The locality sets of phases can be inferred by applying a distance function to a program’s address trace observed during a backward window.
3.  Memory management is optimal when it guarantees each program that its locality sets will be present in high-speed memory.


### 请求分页的机制 {#请求分页的机制}

相比于基本分页系统，请求分页系统的页表需要提供更多信息，因而需要增加字段

-   该页是否已经调入内存 → 状态位 P
-   若未调用，该页在外存中的位置 → 外存地址
-   进程访问页的次数、频率或者其他特征，从而可以参考特征进行页面置换 → 访问字段 A
-   是否修改，从而决定是否写入外存 → 修改位 M

请求分页系统的外存分为两部分：用于存放文件的文件区（离散分配方式）和用于存放页面的交换区（连续分配方式）。

交换区：在 Linux 中，swap 既能以分区形式存在，也能以 swap 文件存在。后者看起来在文件区，但是内核将其作为连续块使用。


### 请求分页的策略 {#请求分页的策略}


#### 页面置换算法 {#页面置换算法}

-   OPT：淘汰以后永不使用或在最长时间内不再被访问的页面。仅有理论意义。
-   FIFO：可能出现 Belady 异常（参见局部性原理一节）
-   LRU：性能接近 OPT，但实现需要硬件支持，开销较大。
-   CLOCK/NRU：参考页面的访问位，当页面被访问时，set 访问位。系统将所有页框组织为一个循环队列，并维护一个替换指针；当需要进行替换时，遍历队列，当访问位为 1 时 clear 并跳过，当访问位为 0 时进行置换。
    -   改进的 CLOCK：同时参考（访问位，修改位）。第一轮扫描，寻找未访问也未修改的页面进行置换。若失败，则进行第二轮扫描，寻找未访问（但修改过）的页面进行置换，同时将访问位为 1 的页面 clear。第二轮若失败，此时所有页面已经被设置为未访问，重复一二轮的扫描。


#### Belady 异常与栈型替换算法 {#belady-异常与栈型替换算法}

Belady 异常：对同一个页面访问序列，给进程分配的页框数增加，缺页次数反而可能增加。

为什么 FIFO 会出现 Belady 异常：FIFO 淘汰的是驻留时间最长的页面，从而一个页面什么时候被淘汰，取决于它什么时候被装入，而什么时候被装入又取决于历史上每一次缺页发生的时间。页框数增加，不是简单的增加容量，而是影响了整个缺页发生的时间线。因而不同页框数下的驻留集合互不包含。 **缺页次数对页框数没有单调性可言。**

栈型替换算法

LRU 在任意时刻的内存集合，就是访问序列中最近出现的 k 个不同页面，取决于序列本身，与页面替换的历史无关。k 个最近使用的页面集合总是 k+1 个最近使用的页面集合的子集，称之为栈型替换算法。满足这种性质的算法，缺页次数必然随着页框数的增加单调不增。


#### 抖动、工作集 {#抖动-工作集}

抖动（thrashing）：进程分配到的页框数少于它当前活跃使用的页面数，于是频繁缺页，花在页面换入换出上的时间超过实际执行的时间。若进程换页时间多于执行时间，就称该进程在抖动。

工作集：某段时间内，进程实际访问的页面集合。

驻留集大小不应小于工作集大小。局部性原理保证一个阶段中工作集近似稳定，从而保证系统动态分配驻留集减少抖动的可能性；但同时，在不同阶段切换时，工作集大小可能出现突变，这时候更易发生抖动。


#### 页框分配 {#页框分配}

进程的最小页框数：指令集上任意一条指令、在最坏对齐下的一次执行中，必须同时驻留内存的页数的最大值。

驻留集：os 决定为进程分配的页框数

页框分配策略：

-   固定分配局部替换
-   可变分配全局替换。当进程发生缺页时，系统首先从空闲页框队列中进行分配，若没有页框空闲，则从系统所有页框中选择一个换出。
-   可变分配局部替换。os 会根据进程缺页率，动态调整驻留集大小。


### 物理页框分配 {#物理页框分配}


#### Linux 物理页框分配 {#linux-物理页框分配}

Linux 内核将物理内存按照地址范围分成几段管理：

-   DMA (0-16MB)：兼容只能产生 24bit 地址的 ISA 设备
-   DMA32 (16MB-4GB)：兼容只能产生 32bit 地址的 32bit DMA 设备
-   Normal (4GB--)：没有寻址限制的普通用途内存

注意：

-   前两个 zone 并不意味着一个普通分配请求不能分配在这里，当 Normal zone 无法分配时，会尝试 DMA32 zone，如果仍然无法分配，继续尝试 DMA zone。
-   现在仍然有大量设备使用 32 位 DMA 掩码，例如 Radeon 780M，USB 控制器，一些 NVMe/网卡等等。

Linux 使用 Buddy System 管理物理页框分配（详情参见 man proc_buddyinfo），按照 2^order \* PAGE_SIZE 将物理内存组织为连续块。

-   进程缺页发生时，内核向 Buddy System 申请一个页框（order-0 块）
-   DMA 请求 16\*PAGE_SIZE 的连续块，Buddy System 进行分配
-   用户程序通过 mmap 申请一个 2MB 大页，内核向 Buddy System 查找一个 order-9 的连续块。


#### Windows 物理页框分配 {#windows-物理页框分配}

按照页的状态组织链表：空闲、已清零、备用、已修改。物理页框在状态队列之间流转。需要连续物理内存时，在页框数据库中搜索凑齐。


### 内存映射文件（Memory-Mapped Files） {#内存映射文件-memory-mapped-files}

内存映射文件是 os 向应用程序提供的一种调用机制，可以将磁盘文件映射到进程虚拟地址空间的某一区域。

1.  可以像访问内存一样读写文件，无需调用文件 I/O 接口。
2.  可以通过将同一文件映射到多个进程的虚拟空间实现共享内存。

mmap vs read/write:

1.  read 的数据路径为，磁盘-内核页缓冲区-用户缓冲区，数据要复制两次；mmap 只需将磁盘文件映射到进程地址空间，后续进行页面请求。
2.  mmap 按需调页，不必完整读入文件。
3.  mmap 有建立映射，填写页表，访问新页的缺页异常等开支；对于小文件而言，read 更高效。
4.  read 顺序吞吐；mmap 靠缺页触发，顺序大流量吞吐更低效。
5.  mmap 写回时机不可控，修改内存什么时候写盘由内核决定；write 返回时已经明确写入。
6.  mmap 难以进行错误处理，错误会以异步信号的形式返回；而不是明确的返回值。
7.  mmap 通用性差，依赖的是 os 提供的系统机制；read/write 面向的是字节流抽象，管道、socket、终端、设备都可使用。数据库等系统的设计也主要依赖 read/write 加自建缓存机制的做法。


## x86-64 架构下的页式管理 {#x86-64-架构下的页式管理}

x86-64 ISA 规定物理地址上限为 52 位（MAXPHYADDR=52）。以 4KB 页面大小为例，52 位划分为：低 12 位标志位，高 40 位页框号。因而 PTE 长度对齐到 8B。

x86-64 ISA 规定虚拟地址位数为 48bit（四级页表） or 57bit（五级页表）

> 注意：
>
> -   页框号位数是可变的（但总是在高 40 位中），但 PTE 长度是 ISA 规定的，保持 8B 不变。
> -   页框号实际能用到的位数由 CPU 物理地址宽度（48 bit-&gt;36 bit）+实际内存大小（32GB 内存-&gt;23 bit）决定。
> -   x86-64 规定物理地址上限为 52 位，但当前一般 CPU 物理地址为 48 位。
> -   PTE 对齐到 8B 后，有 64-52=12 位可以使用。例如 63 位用来标志栈所在页不可执行，防范缓存区溢出攻击。而 52-58 位留给操作系统使用，Linux 用 55 位做 soft-dirty 追踪。

页表级数由虚拟地址位数决定，与物理地址无关：页表将虚拟页号翻译为页框号，是从虚拟地址出发查表的，物理地址只决定页框号位数。每页可以容纳 4KB/8B=2^9 个页表项，因而 **级数=（虚拟地址位数-页内偏移位数）/页表偏移位数**

-   虚拟地址 48 位：\\(2^{48}B=4KB\times ({2^9})^4\\)，应当采用 4 级页表。
-   虚拟地址 57 位：\\((57-12)/9=5\\)，应当采用 5 级页表。
